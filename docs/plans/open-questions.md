# أسئلة مفتوحة — محسومة

كل الأسئلة التي طُرحت أثناء التخطيط تمت الإجابة عليها من المستخدم. هذا الملف يوثّق القرار النهائي لكل سؤال، للرجوع إليه لاحقاً دون الحاجة للرجوع للمحادثة الأصلية. التفاصيل التقنية الكاملة لكل قرار موجودة بملفات المراحل المرتبطة (مُشار إليها أدناه).

## 1. migration جدول `currencies`

**القرار:** يُحذف الملف مباشرة بدون قلق بخصوص بيئات سابقة. لا حاجة لـ `drop_currencies_table` migration منفصل.
→ `phase-1-cleanup.md` خطوة 1.4

## 2. حذف موظف/تابع

**القرار:** الأدمن (بصلاحية `employees.delete`/`dependents.delete` عبر `RoleUser`) يحذف/يعدّل بحرية كاملة بدون قيد أعمال إضافي مسبق. الاستقبال بدون هذه الصلاحيات إطلاقاً (لا حذف ولا تعديل، عرض فقط). حماية الـ FK (`restrictOnDelete`) تبقى كخط دفاع تقني فقط.
→ `phase-5-entities.md` §5.3، `phase-2-auth-authorization.md` §2.4

## 3. حذف الزيارة

**القرار (مُعدَّل عن التوصية المبدئية بمنع الحذف كلياً):** حذف مباشر (hard delete) مسموح فعلياً. مستخدم بصلاحية `visits.delete` العامة (افتراضياً الأدمن) يحذف أي زيارة. مستخدم بصلاحية `visits.delete-own` فقط (افتراضياً الاستقبال) يحذف فقط الزيارات التي سجّلها بنفسه (`recorded_by = هو`). لا حالة "ملغية" وسيطة. كل حذف يُسجَّل بـ `activity_logs`.
→ `phase-2-auth-authorization.md` §2.4 (تفصيل `VisitPolicy`)، `phase-5-entities.md` §5.5

## 4. سبب رفض طلب الاستبيان

**القرار:** لا يوجد حقل سبب رفض إطلاقاً — رفض بسيط (`status='rejected'` + `reviewed_by` + `reviewed_at`) بدون أي إدخال إضافي.
→ `phase-6-workflows.md` §6.3

## 5. حماية حذف/تعطيل حسابات المستخدمين

**القرار:**
- ممنوع أي مستخدم يحذف حسابه الخاص، دائماً وبدون استثناء.
- `super_admin = true` يحذف أي حساب آخر (يتجاوز كل القيود التالية).
- مستخدم `role=admin` عادي (بدون `super_admin`) **لا** يقدر يحذف حساب `role=admin` آخر، حتى لو يملك صلاحية `users.delete` عبر `RoleUser`.
- مستخدم استقبال بصلاحية `users.delete` الممنوحة له صراحة (غير افتراضية) يقدر يحذف حسابات أخرى، ضمن نفس قيد "لا يحذف أدمن" أعلاه.
→ `phase-2-auth-authorization.md` §2.7

## 6. مصطلحات الـ nav بالعربي

**القرار:** استخدام المصطلحات الصحيحة/المعتمدة فعلياً بالمؤسسة (تُحسم أثناء التنفيذ الفعلي، ليست عائقاً — التعديل سلس لاحقاً لو احتاج تغيير).
→ `phase-4-layout-navigation.md` §4.1

## 7. `check.cookie` middleware

**القرار:** تأكيد أنه كود ميت غير آمن، لا يوجد سبب تشغيلي خفي له (لا SSO، لا تكامل خاص) — يُحذف بالكامل ويُستبدل بـ middleware `auth` القياسي.
→ `phase-1-cleanup.md` خطوة 1.1

## 8. نظام `RoleUser`/`data/abilities.php`

**القرار (يُلغي التوصية المبدئية بالاعتماد على `role` فقط):** يُستخدم نظام `RoleUser` الموجود فعلياً كآلية الفحص الفعلية لكل الصلاحيات — صلاحيات جزئية فعلية لكل مستخدم، وليس فقط فحص `role`. عمود `role` يبقى فقط للتصنيف العام ولتحديد الصلاحيات الافتراضية عند إنشاء مستخدم جديد (قابلة للتعديل يدوياً بعدها). السبب: أمرن وأسهل من قفل كل شي بمنطق دورين ثابت، ويسمح بحالات استثنائية (مثال: استقبال بصلاحية حذف مستخدمين) بدون تعقيد إضافي بالبنية.

**تأثير هذا القرار على باقي الخطة:** غيّر بشكل جوهري خطوة 2.3 و2.4 بـ `phase-2-auth-authorization.md` (لا يوجد bypass عام لـ `role=admin` عبر `Gate::before` — فقط `super_admin` يبقى bypass، وكل الصلاحيات الأخرى تُمنح فردياً عبر `RoleUser`)، وأثّر على `data/abilities.php` (يصير ملف مستخدَم فعلياً، تُضاف له مجموعات الكيانات الجديدة).
→ `phase-2-auth-authorization.md` §2.3 و§2.4 (التفصيل الكامل)
